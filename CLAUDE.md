# CLAUDE.md

Decompilation of *Logical Journey of the Zoombinis* (Broderbund, 1996, Windows release). The long-term goal is source code that builds and runs on modern systems. See `README.md` for the public-facing overview and quick start, and the handbook in `docs/` (https://docs.zoombinis.online) for everything else.

## Key facts about the target

- **Main binary (target):** `zoombi32.exe`, the Windows 95 build, extracted by `uv run extract-game` from the game ISO (via `ZBARCHIV.Z`, an InstallShield 3 archive) into `build/zoombi32/`. PE32, ~634 KB, sections `CODE`/`DATA`/`.idata`/`.edata`/`.reloc`/`.rsrc`.
- **Compiler:** Borland C++ 4.5 or 4.52, which generate identical code for this game; the tools use 4.5. **Options: `-p -k-`** (Pascal calling convention by default; no stack frame unless needed) plus BCC32's defaults (no optimisation, register variables, byte alignment), confirmed by matching functions (see `docs/src/concepts/compiler.md`). So decompiled game functions have no calling-convention keyword and list their parameters in Pascal order: **Ghidra shows them reversed** (its `param_1` is the last parameter). Options were set per module: the support library at `0x46d754`-`0x46f7a4` (the Mohawk OS layer, `decomp/os_*.cpp`) used `-p` alone, and the Mohawk engine declares conventions per function (its QuickDraw-style modules match with the game's `-p -k-`; its classes' methods don't pop their arguments); files that differ set their own options with `/* @flags ... */`. Linked by TLINK32 (PE linker version 2.25); the PE timestamp (2013) is junk.
- **Imports:** KERNEL32, USER32, GDI32, ADVAPI32, WINMM (the import table). Loaded at run time by name (`LoadLibrary`): DSOUND (DirectSound, `wavebuf`), and QTIM32 + CMGR32 (QuickTime for Windows 2.x, 32-bit) and VERSION, by the QuickTime glue.
- **Assets:** `DATA/*.MHK` on the disc (`build/disc/DATA/` after extraction), Mohawk archives (`MHWK` magic, `RSRC` directory), read from the CD at runtime. ScummVM's `engines/mohawk/` is the reference for the container format; per-game resource types for Zoombinis are undocumented.
- **Other build:** `ZOOMBINI._EX` on the disc is the Windows 3.1 build (Win16 NE, same compiler family). Useful for cross-reference, not the primary target.
- **Ignore:** installer and autorun files (`MS*`, `_INST32I.EX_`, `SETUP.*`, `INSTALL.EXE`, `AUTORUN.EXE`).

## Constraints

- **Reproducibility:** every setup step a developer needs after cloning must be committed or performed by a script. The only manual inputs are bring-your-own files (the game in `data/`, Windows install media). Exploratory work is fine, but always finish by folding it into a script and documenting it in the handbook's Setup chapter (`docs/src/getting-started/setup.md`; the README keeps only a quick start).
- **Legal:** `data/` is gitignored and holds the user's ISOs (game disc and Windows 98 SE, default names in `src/zbtools/paths.py`); `.env` holds their Windows product key (`WINDOWS_PRODUCT_KEY`). Never commit the game's original files (the disc, its executables, the `.MHK` archives as shipped), Windows media, or large verbatim disassembly of the original binaries. The game's resources, extracted and converted to modern formats (PNG, WAV, MIDI, text), are the exception: like the decompiled code, they are the project's source, committed under `assets/` and packed back into Mohawk archives by the tools.
- Treat `data/` as read-only. Write extracted or derived output to the gitignored `build/` directory.
- Host platform: macOS on Apple Silicon. Rosetta 2 cannot run 16-bit Windows code, so Wine cannot run the game (the QuickTime installer needs 16-bit code); use the emulated VM instead. Wine *is* used for the 32-bit Borland command-line tools (`uv run toolchain`).

## Layout

- `src/zbtools/`: Python tooling package. Each tool is a module exposing `main()`, registered under `[project.scripts]` in `pyproject.toml` and run as `uv run <name>`.
- `src/zbtools/paths.py`: default locations of inputs and outputs, resolved from the repo root. New tools should take their defaults from here and allow overriding them with arguments.
- `build/`: gitignored output (`build/disc/` = disc contents, `build/zoombi32/` = Windows 95 build, `build/vm/` = VM disks).
- `src/zbtools/host.py`: the only place that knows about the host OS (binary locations and install hints, QEMU display/audio backends). Route any new host-specific behaviour through it.
- `src/zbtools/vm.py`: `uv run vm`. `install` builds a read-only Windows base disk (unattended Windows 98 SE setup driven by a customized boot floppy + MSBATCH.INF); `install-game` layers QuickTime and the game on it; `run` boots a throwaway qcow2 overlay on top; `reset` discards the overlay. VM automation (watching the screen, typing) goes through QMP with `qemu.qmp`.
- `src/zbtools/toolchain.py`: `uv run toolchain`. Extracts `{BIN,LIB,INCLUDE}` from each Borland CD's run-from-CD tree (`BC45/` for 4.5x, `BC5/` for 5.02; `toolchain.RELEASES`) with 7-Zip into `build/toolchain/<release>/`, maps each release to a Wine drive (4.5 = `T:`, 4.52 = `U:`, 5.02 = `V:`, the repository = `R:`, host root = `Z:`; the Borland tools truncate paths over 80 characters, so `toolchain.windows_path` puts paths in the repository on `R:`) and rewrites its BCC32.CFG/TLINK32.CFG to match; runs tools under Wine with the release's `BIN` on the Windows PATH (BCC32 finds TLINK32 via PATH). Borland `.OBJ` files embed timestamps and include paths in COMENT records, so object comparisons must ignore those.
- `src/zbtools/game_install.py`: builds the "tools CD" that `install-game` runs inside the VM. `src/zbtools/screen.py`: recognisers for Windows screens (logon prompt, idle desktop).
- `decomp/`: decompiled C++ (`.cpp`; the game is C++). Mark each decompiled function with `/* @zoombi32 0x<address> */` immediately before it; `uv run match` (`src/zbtools/match.py`) compiles each file (with its release: 4.5 unless the file says `/* @release 5.02 */`; caching objects in `build/match-cache/`, keyed on the source, the local headers it includes, its options and the release) and compares marked functions byte for byte, masking linker-filled fields (it uses `omf.py`, a minimal OMF object reader, and `exe.py`, typed pefile/capstone wrappers). **Naming:** rename a function, global or struct field as soon as its purpose is clear, so its callers read better; until then name it after its address (`fn_46be2e`, `g_4a7f58`). Functions, variables and fields are camelCase (`isMousePresent`, `currentTimeMs`) and types PascalCase, matching the engine's own class names (`basePort`, `fileSpec`); names recovered from RTTI or runtime symbols are used exactly. Prefer honest, specific names over guesses at the originals, and rename freely as understanding improves: the marker holds the address, so the tools don't care. `uv run ghidra label` copies decomp/ names into Ghidra (not over names set by hand there), and the worklist and report show them. Declarations live in headers, globals by address: a module's function prototypes, and the globals and types only its code uses, go in `decomp/<module>.h`, which its source and its callers' sources include after `decomp/zoombinis.h`; shared types, and everything else (engine, OS layer, runtime, globals several modules use), go in `zoombinis.h`. Keep it that way as you add declarations: `match` caches objects by the headers each source includes, so a change to `zoombinis.h` recompiles every file while a change to a module's header recompiles only the files including it. Declare each function and global once (a test checks; two functions sharing a name each carry their address, `/* 0x46daca */`). `uv run includes` (`src/zbtools/includes.py`) sets each source's module-header includes to the ones declaring names it uses. A renamed global keeps its address in a marker: `extern long mousePresent; /* @data 0x4a7f58 */`. `uv run ghidra label` gives Ghidra the headers' structs (category `/zoombinis`) and their globals' names and types (`src/zbtools/declarations.py` reads the headers), so keep them plain: structs, `extern` globals and prototypes. Whether a function matches is measured, never declared: `decomp/matching.txt` (written by `uv run match --update`, which you run after changing `decomp/`) records what matches, and `uv run match` fails if a recorded match regresses. A decompiled function is only done when it matches; one that doesn't yet gets a comment saying what still differs. **Decompiled code must be portable C++** that could be rebuilt for a modern system: no inline assembly, `__emit__`, pseudo-registers (`_EAX`, `_EBP`) or reliance on the x86 stack layout; calling the Windows API is fine. Where only machine code would reproduce the original exactly, write the portable equivalent and mark it `/* @zoombi32-functional 0x... */` (complete, deliberately not byte-exact), with a comment on what the original does; if there's no portable equivalent, leave a documented stub (it simply won't match). A function the compiler generates itself (an implicit destructor) has no definition to mark: name it in a marker of its own in the file whose object holds it, `/* @zoombi32-implicit 0x0048a6f9 DIB8Port::~DIB8Port */`, and `match` measures it all the same; a global object's construction and destruction calls (unnamed functions the object's `_INIT_`/`_EXIT_` segments list) are `<startup>` and `<exit>`, in the file defining the global. Keep pointers typed as pointers where known (not `long`), for an eventual 64-bit build. Don't replace what standard C++ reserves (the global placement `operator new(size_t, void *)`): compilers assume it and skip the replacement, so the game's zeroing placement new is `audioObj`'s. Headers next to a source file can be included (`match` adds the source's directory to the include path).
- `src/zbtools/match_data.py`: `uv run match-data`, the data counterpart of `match`: places the pieces of every compiled data segment (`_DATA`, `_BSS`, vtables) in the original's DATA section by `@data` addresses, matching functions' references and pointers from placed data, and compares them (docstring for the rules); it also checks that every data reference in the decompiled functions points where the original's does (`match` masks those addresses, so a function can match while reading the wrong global). `report` shows its totals and any wrong references. Defining the game's globals (with their initial values) moves them from declared to defined, placed and matching.
- `src/zbtools/define_data.py`: `uv run define-data` defines the globals the headers declare but no source defines, in their owning module (by the original's references), with initialisers rendered from the original's bytes by a small model of our headers' types (checked against BCC32's `sizeof` through a probe file in `build/match-cache/probe/`); data that initialised pointers point to but nothing declares, it declares in the module header of the data around it (`g_<address>`); it lists what it leaves for a person. Rerunning it only adds what's missing. A declaration whose type runs into the next global is usually an array the code indexes from 1 (declared an element early) or a second name for one of its elements: fix the declaration, rewriting uses as the real array's elements (the same address compiles to the same code).
- `src/zbtools/build.py`: `uv run build` compiles `decomp/` and `glue/` (with `match`'s objects), the icon (`exe_resources.resource_script`, BRCC32), and links them with TLINK32 1.50 (the original's linker; its default 64 KB section alignment and GUI options are the original's) in the original's order (sources by their first marked function; `glue/` by the code it stands in for) into `build/rebuild/zoombi32.exe`, with a map. `glue/`: C++ standing in for what the game links but we don't have (QuickTime's SDK glue: `glue/quicktime.cpp`, which plays no movies yet); it isn't decompiled code, so it has no markers, `match` ignores it, and it may use inline assembly where the interface needs it (QuickTime's stubs pass their selector in `bx`).
- `src/zbtools/exe_resources.py` + `src/zbtools/formats/icon.py`: the executable's resources (its icon) in `assets/zoombi32/` (`ICON/<id>.png`, `resources.toml`), extracted and verified by `uv run assets` and compiled by `uv run build`.
- Testing the rebuilt game: `uv run vm run --exe build/rebuild/zoombi32.exe` (carried on a floppy, copied into the game's directory as `REBUILT.EXE` and started); `--trace <log>` has QEMU log the executable's code as it runs (filtered to its addresses, stopping at 500 MB or 2 minutes), and `uv run trace <log>` (`src/zbtools/trace.py`) names the functions from the map, the last being where it crashed. A near-miss can be the bug: check what differs in the functions a crash is in. The game refuses to start while its global atom "Zoombini" exists, which a crash leaves behind: reboot the VM before running it again.
- `port/` + `src/zbtools/port.py`: `uv run port` (`setup`, `build`, `package`, `run`, `serve`; each takes a *target*: `macos_universal`, `windows_x86`, `windows_x64`, `linux_x64`, `linux_arm64`, `browser_wasm` or `headless_wasm`, defaulting to the machine's own; any builds from any host: Xcode, llvm-mingw, a Docker container, Emscripten). The decompiled game built for modern systems with CMake and SDL2 (handbook: "The port"). `decomp/` compiles unchanged: `port/include/` is *miniwin*, the Win32 subset the game uses (`windows.h`, `mmsystem.h`, Borland's `dir.h`/`dos.h`; everything in `namespace miniwin`), with `miniwin/prelude.h` force-included to read Borland's dialect (byte packing, signed chars); `port/miniwin/` implements it over SDL (one host thread, Win32 threads and the engine's fibers switched cooperatively; `service()` does what Windows did in the background). `port/host/` is the only per-target code (fibers, yielding to the browser, message boxes) and never includes miniwin's headers. Match Windows 95's behaviour where the game relies on it (16-bit `0xFFFF` counts and device ids, a click activating a window). A file in `port/decomp/` replaces `decomp/`'s of the same name; use it only where the portable version must differ. The decomp keeps Borland's 32-bit `long`: pointers held in integers are `LONG_PTR`, and where `long` is 64 bits (Linux, macOS) `prelude.h` makes the game's `long` an `int` (handbook: "64-bit targets"), so write sizes as `sizeof`/`offsetof`, never numbers. `uv run port package` packs a target for players (`src/zbtools/bundle.py`: a macOS `.app` in a `.dmg`, else a directory in a `.zip`/`.tar.gz`; the program finds `game/` beside itself) or, for `browser_wasm`, writes the site. Debug tooling (`port/debug/`, text commands: jump to a scene, set levels, fill the party, edit `gameState`; `--cmd`, `--script`, `?cmd=`, `zbDebug()`) is built when `ZB_DEBUG` is defined, whose only trace in `decomp/` is an `#ifdef ZB_DEBUG` hook in `gameFrame` (handbook: "Debug tools"; keep any new hook in `decomp/` behind it, so `match` is unaffected). Debug with the headless build under Node: `uv run port run headless_wasm --seconds N --screenshot F.bmp`. `uv run port package browser_wasm` writes the hostable site to `build/port/dist/browser_wasm/` (only the files a server needs, each under 24 MiB: `port.SITE_FILE_LIMIT`; bigger files are split into `.part<n>` files that `port/web/pre.js` joins at startup), with D:'s archives packed from `assets/` and C: laid out from `assets/zoombi32/installed/` (`mohawk.w32`, the font `CORNER.TTF` and the saved-game list `Zoombini.who`, converted to TOML by `formats/roster.py`; committed by `uv run assets extract`, so `package` needs only the repository).
- `src/zbtools/near_misses.py`: `uv run near-misses` sorts the near-misses by what differs: the same computations (allocation only), address-taken locals laid out differently (check their sizes), or different computations (listed). Measures each original function to its epilogue's `ret` (Ghidra's sizes stop short at switch tables). Review a near-miss with more than allocation differences before trusting it.
- `src/zbtools/ghidra.py`: `uv run ghidra`. Pinned Ghidra release (built natives on platforms without prebuilt ones, e.g. Apple Silicon, via Ghidra's Gradle wrapper), driven headlessly with `pyghidra`; `ghidra-stubs` (same version) types the Ghidra API for mypy. Ghidra classes can only be imported after `pyghidra.start()`, so import them inside functions (with `# noqa: PLC0415`) and under `TYPE_CHECKING` for annotations. The stubs don't model Java's nulls: where a Ghidra method can return null, annotate the variable as `X | None` explicitly. The project in `build/ghidra/project/` may hold the user's manual reverse-engineering work: never delete or recreate it without being asked. `download.py` holds the shared pinned-download helper (Wine and Ghidra).
- `src/zbtools/runtime_symbols.py`: `uv run runtime-symbols` names the Borland runtime code in the game by matching library code segments (see `docs/src/reference/runtime-and-rtti.md`); `uv run ghidra label` applies the names, never overwriting names set by hand.
- `src/zbtools/rtti.py`: `uv run classes` recovers C++ classes from Borland RTTI type descriptors (layout in the module docstring and `docs/src/reference/runtime-and-rtti.md`) into `build/symbols/classes.json`; `uv run ghidra label` turns them into Ghidra classes, names functions after their decomp/ versions, and sets `__stdcall` where functions pop their own arguments. Automated naming never overwrites names set by hand in Ghidra (source USER_DEFINED).
- `src/zbtools/demangle.py`: Borland C++ demangler (`demangle`, `qualified_name`), checked against Borland's TDUMP; used by `match`, `runtime-symbols` and `ghidra label`.
- `src/zbtools/inventory.py`: every function with its region (startup / game / runtime / engine, derived from the recovered symbols), direct and indirect calls, and status as recorded (matched / nonmatching / functional / library / todo; `report` also measures, and badges disagreements). Used by `uv run worklist` (what's ready to decompile, leaf-first) and `uv run report` (HTML progress report in `build/report/`, built with Jinja2 from `src/zbtools/templates/`). The report contains the game's disassembly: never publish it (no Artifacts, uploads or commits).
- `src/zbtools/modules.py` + `decomp/modules.toml`: `uv run modules`. The source modules (object files) of the game and of the Mohawk engine (whose modules are small, often one function each), a curated map of start addresses and names checked against the zero padding TLINK32 puts after each module's code; the inventory gives each function its module, the worklist can filter by it (`--module`, which implies the module's region) and the report shows progress per module. Decompiled functions go in `decomp/<module>.cpp`. Name modules by evidence (strings, `.MHK` files, imports), else by address (`module_4124a4`), and record the evidence in `note`.
- `src/zbtools/quicktime.py`: QuickTime for Windows' SDK glue linked into the game (`0x46cca0`-`0x46d754`): its loader functions and per-selector dispatch stubs, named by `uv run ghidra label` and treated as library code by the inventory.
- `src/zbtools/mohawk.py` + `src/zbtools/assets.py` + `src/zbtools/formats/`: `uv run assets`. `mohawk.py` reads and writes Mohawk archives exactly as the game's are laid out (rejecting anything it couldn't reproduce). `assets extract` writes each archive on the disc into `assets/<archive>/` (committed: the resources are source, like `decomp/`): `archive.toml` (its path on the disc and its resources in stored order) and each resource as `<type>/<id>.<extension>`, converted by its type's `Format` (`formats.FORMATS`: WAV, PNG, MIDI, `.cur`, TOML). **Only ever one copy of a resource is committed**: its modern form, or the original bytes (`.bin`) only where no format fits. A format must round-trip exactly: `extract` saves a resource, loads it back and keeps it raw if the bytes differ, and `assets verify` rebuilds every archive and compares it with the disc byte for byte (the `match` of the assets), so keep it passing. Formats re-create Broderbund's encoders (Okumura's LZSS, the row packer) rather than any valid encoding, and record in TOML what can't be derived (junk bytes); a format may use the rest of the archive only for viewing (an image's display palette), never for what `load` needs. The LZSS encoder is slow in Python, so compressed images are cached in `build/assets-cache/`, holding only the encoder's own output (never the disc's bytes, or `verify` would test nothing).
- `src/zbtools/movies.py` + `src/zbtools/formats/mov.py` + `src/zbtools/formats/qkbk.py`: the movies, in `assets/movies/<NAME>/` (committed, part of `uv run assets`: `extract`, `pack`, `verify`, and `frames` to draw frames as PNGs). `mov.py` reads and writes the `.MOV` container exactly (`MovInfo` holds what can't be derived); `qkbk.py` the `QkBk` frames (a scene: sprites from a cast of bitmaps and palettes, not pixels; its docstring is the format's reference) with Broderbund's run-length encoder re-created; `movies.py` turns a movie into `frames.toml`, `palettes.toml`, `bitmaps.toml`, `casts/<id>.png`, `sound.wav` and `movie.toml` and back. Same rule as the other assets: one copy, exact round trip, `verify` is the `match` of the movies. `uv run ghidra codec` imports the codec `qb32.qtc` into its own project and writes Ghidra's C for it to `build/ghidra/qb32.c` (the original's code: never commit it). `src/zbtools/qb32.py` (`uv run movie-check`) runs `qb32.qtc` itself under emulation (`src/zbtools/x86.py`, typed wrapper for Unicorn) and compares the frames it draws from the movies built from `assets/` with `qkbk.render_frame`'s. The rebuild's `glue/quicktime.cpp` loads the real QuickTime (selector stubs as `__emit__` bytes); the port's `port/glue/quicktime.cpp` replaces it with a player of the scene file `formats/scene.py` writes (`uv run port package`/`run`).
- `src/zbtools/shots.py` + `docs/screenshots.toml`: `uv run shots [ID...]` captures the handbook's screenshots from the headless port: a recipe per placeholder id (debug commands ending in `quit`, optional `seconds` and `crop`), run in parallel on fresh C: drives, written to `docs/src/images/<id>.png` (palette PNGs, 640x480 or cropped) and embedded; needs `uv run port build headless_wasm`. Add a recipe with each placeholder you can reach.
- `src/zbtools/visual.py` + `tests/visual/`: `uv run visual [CASE...] [--rebaseline]`, visual regression tests: `tests/visual/cases.toml` has debug-command scripts (`screenshot NAME` takes a picture, `assert` checks the game's state; each starts with `seed` and sticky mouse off, and ends itself) that the headless port plays in parallel on fresh C: drives; the pictures are compared with `tests/visual/baselines/<case>/<NAME>.png` (palette PNGs, checked in; a pixel differs past 24/255 per channel, a picture fails past the case's 0.5% tolerance; a differing case is replayed once). `--rebaseline` writes the changed pictures and removes baselines no case takes. Every run writes `build/visual/report.html`, one self-contained file with the baseline, new picture and highlighted differences of each failure (and `--summary FILE` appends Markdown, which the PR pipeline's `visual` job gives to GitHub's job summary; the report is uploaded unzipped as `visual-report.html`). `tests/test_visual.py` (in `uv run lint`) checks that cases and baselines agree. Add a case with each flow worth guarding; rebaseline and commit the pictures when a change is meant to alter them.
- `docs/` + `src/zbtools/book.py`: the handbook, an mdBook (`docs/book.toml`, chapters in `docs/src/`, listed in `docs/src/SUMMARY.md`; output in `build/book/`). `uv run book build|serve|screenshots` (`screenshots --update` regenerates the index of screenshot placeholders in the appendix; a test checks that it is current, that every chapter is in `SUMMARY.md` and that relative links resolve). It holds the confirmed facts about the game, formats, compiler and port, with the evidence (addresses, strings, experiments), and the gameplay-to-code map.
- **Keep `uv run clean` up to date:** it deletes by category, from `paths.CLEAN_CATEGORIES`. Every path a tool generates must belong to a category (categories may include other categories by name); add new ones there, and to `CLEAN_DEFAULT` if they're cheap to rebuild. Keep the cleaning table in the handbook (`docs/src/reference/cleaning.md`) in sync.

## Game plan

1. Scripted Windows 98 VM under QEMU that runs the game, for dynamic analysis (QEMU's gdbstub for debugging).
2. Mohawk extractor and catalog of resource types per archive.
3. Ghidra project for `zoombi32.exe`: label imports, identify Borland RTL functions via signatures.
4. Toolchain spike: Borland C++ 4.x 32-bit compiler run headless, plus a diff tool comparing compiled objects against original functions with relocations masked. Time-box this.
5. Decompile function by function, starting with small leaf functions. **Functional (non-matching) first**; byte-matching is a goal where practical, not a gate.
6. Port off QuickTime/DirectSound/256-colour GDI to a modern platform layer.
7. The intro movie (done): reverse-engineer Broderbund's `QkBk` codec (`qb32.qtc`) and convert the movie to a modern format and back, byte for byte, like the other assets. The Windows 98 rebuild plays the `.MOV` packed from `assets/` through the VM's QuickTime (real glue, inline assembly allowed); the ports play the modern form directly, with no QuickTime.

## Code quality

Run `uv run lint` (ruff lint, ruff format check, mypy, pytest) before finishing any change to Python code; `uv run lint --fix` applies ruff's fixes and formatting first. It must pass cleanly. It also runs as a pre-commit hook (`.pre-commit-config.yaml`, installed with `uv run pre-commit install`); never bypass it with `--no-verify`.

- **Strict typing:** mypy runs in strict mode with `disallow_any_explicit`. Annotate every function, and every variable whose type isn't inferred. Never write `Any`, `cast()` or `# type: ignore` to silence mypy; fix the types instead.
- **Model structured data with types, not dicts:** `@dataclass(frozen=True)` for records built in code, `NamedTuple` for small immutable tuples, `TypedDict` for dict-shaped data that must stay a dict, and **pydantic models** wherever data from outside the program (JSON, protocol messages, files) needs validating at runtime (e.g. the QMP models in `vm.py`).
- **CLIs use Typer:** each tool module defines `app = typer.Typer(...)` with typed command functions (`Annotated[..., typer.Option(...)]`), registered in `[project.scripts]` as `zbtools.<module>:app`.
- **Binary parsing:** prefer typed helpers such as `int.from_bytes` over `struct.unpack_from`, which returns untyped tuples. `struct.pack_into` is fine for writing.
- Use `pathlib` rather than `os.path`. Use `# fmt: off`/`# fmt: on` only around data tables that formatting would make unreadable.
- **Don't reinvent wheels.** Before hand-writing a parser, file-format reader, protocol client or similar, check PyPI for a maintained library that ships wheels for our Python version (and type information, or add a narrow mypy override as for `fontTools`). Current choices: pycdlib (ISO 9660), fontTools (fonts), Pillow (images), python-dotenv (`.env`), `qemu.qmp` (QEMU control), Typer (CLIs), pydantic (validation), Unicorn (x86 emulation of the codec). Where no good Python library exists, prefer a standard host tool routed through `host.py` (e.g. mtools for FAT floppy images; `pyfatfs` and `fatfs` are unmaintained or lack wheels). Only hand-write code when neither exists, and say why in its docstring (e.g. the DCL decompressor in `unpack_isz.py`).
- Tests live in `tests/` (pytest). Add them for logic that can be checked without bring-your-own files (parsers, demangling); anything needing the ISOs or toolchain is verified by running the tools.
- Dependencies: add runtime ones with `uv add`, dev tools with `uv add --dev`.
